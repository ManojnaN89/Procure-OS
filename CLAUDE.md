# P2P platform: rules for working in this repo

An India-first, domain-neutral, multi-tenant procure-to-pay platform (request, approval, sourcing, PO, receipt, invoice match, payment). Built by one developer with Claude Code. The plan lives in `planning/` (git-ignored); the data model is `docs/data-dictionary.md`.

## Layout

| Folder | What |
|---|---|
| `backend/p2p/` | FastAPI app. One package per area: `masters`, `requests`, `approvals`, `sourcing`, `orders`, `receiving`, `invoices`, `suppliers` (scoring), `agents`, `ai_steps`, `rules`, `formulas`, `platform` (API routers, auth, audit, jobs, setup) |
| `ui/` | The main app people work in (Procure-OS): plain HTML, JS and CSS, no build step, served at `/` by the backend. Menu and screens by role |
| `frontend/` | The admin app (React + Vite + TypeScript + Tailwind, Biome): approvals, company setup, automation controls, audit. Built to `frontend/dist`, served at `/admin` |
| `datagen/`, `data/` | Synthetic data generators and reference tables. Generated datasets go to `data/datasets/` (git-ignored) |
| `tests/` | pytest, named after scenarios (given, when, then in the body). `test_web_shell.py` and `test_main_ui.py` are the browser tests |
| `evals/` | Evals E01-E43 against the plan with independent oracles, plus their results (`evals/README.md`) |
| `scripts/` | `dev.py` starts everything, `check.py` runs every check, `capability_matrix.py` summarises `docs/capability-matrix.md`, `gen_schema_doc.py` writes `docs/database-schema.md` (run it after a migration), `audit_deps.py`, `model_eval.py`, `gen_master_schema.py`, `make_key.py`, `measure.py`, `acceptance_browser.py` |
| `docs/` | `data-dictionary.md` (meaning), `database-schema.md` (every table and column, generated by `scripts/gen_schema_doc.py`), `guides/` (one page per role, shown on the Help page), `demo-script.md`, `capability-matrix.md`, `security-review.md`, `dependencies.md`, `model-selection.md` |
| `planning/` | The project plan workbooks (git-ignored) |

## Commands

- Start everything: `python scripts/dev.py` (Postgres and Mailpit in Docker, backend on 8000, frontend on 5173)
- All checks: `python scripts/check.py` (ruff, mypy strict, pytest, biome, tsc). Run before saying a task is done.
- Backend tools use `backend/.venv`. Dependencies: edit `requirements.in` or `requirements-dev.in`, install, then `pip freeze > requirements.txt`.
- Browser tests need `cd frontend && npm run build` and `playwright install chromium` once. They skip when the build is missing.
- Run the job worker (timers, escalations, email, mailbox polling): `python -c "from p2p.platform import worker; worker.run_forever()"` from `backend/`.
- Compare models: `python scripts/model_eval.py --models groq:openai/gpt-oss-20b --out result.json` (live calls, synthetic data only, paced by the gateway).
- Never run two pytest runs at once: they share one test database (a second run needs its own `P2P_TEST_CONTROL_DB` and `P2P_TENANT_DB_PREFIX`, which names its company databases).
- Load a dataset into a company (masters first, then stock history): `python -m p2p.cli import masters <tenant> <dataset> [--dry-run]`, then `import stock ...`, from `backend/`. Each prints every row it left out and why. The first masters import of a company (no import before, no supplier or item yet) replaces its masters; every later one updates by key (`masters/import_rules.py`): new rows are added, changes applied where the table allows, nothing deleted, and what a second person decides (supplier status and bank accounts, policies, rules, roles, approvers, versions, opening stock) is kept, or arrives as a draft or unverified, with a warning.
- Load the ERP's demand (production orders and their component lines, MRP results, sales orders, demand plan, joiner kits and the joiner plan of an office; CSV or Excel in our templates, a client's own column names through the saved mapping `erp_column_map`): `python -m p2p.cli import demand <tenant> <dataset-or-file> [--dry-run] [--kind KIND]`, from `backend/`. A folder is read from its `inputs/`; rows loaded before are skipped (a second import loads nothing); a row sent again with other values, or `status` cancelled, is applied (Q21: requests not yet with the buyer cut, stock released to the next orders, a case for the buyer or the store, the store check run again for more or earlier) and listed with what it did; every bad row with its reason. An MRP plan gets a material request per location (`basis` net lines take no free stock). The demo changes are in `data/datasets/<name>-v1/changes/<scenario>/`.
- The store check (stock set aside earliest need-by first, free stock less safety stock; supply counts only when due by the need-by less `receiving_buffer_days`, rule Q17; what only late supply covers is at risk, a case for the buyer; what nothing covers is bought): `python -m p2p.cli material check <tenant> [--no-submit] [--schedule]` (the daily 05:30 run is queued when a company is made or reset while `auto_store_check` is on, and by `--schedule`; it leaves its requests as drafts unless `store_check_submit` is on); `material explain <tenant> <MR-no>` asks the planning capability (off unless switched on).
- Create draft purchase requests for stock at its reorder point: `python -m p2p.cli replenish <tenant> [--dry-run] [--no-submit] [--schedule]` (creates the requests and sends them through approval; `--schedule` queues the daily run, which creates requests only when the setting `auto_replenishment` is on). Automatic requests need the setting `replenishment_department`: its head is who approves them.
- Decide how approved requests are bought and send the quotation requests: `python -m p2p.cli source <tenant> [--request NO] [--no-send]` (the worker does this by itself when a request is approved). Each line takes the buying route (D37): contract, single source, emergency, safe reorder, else quotation with 1-3 quotes by value; thresholds are versioned rows of `buying_route_rule`. Sending is never automatic (D42): every RFQ waits as a proposal `rfq.send` until a buyer confirms it (one, or several at once on **Quotations**); reminders on a confirmed RFQ run by themselves.
- Remind suppliers who have not answered a quotation request: `python -m p2p.cli remind <tenant> [--dry-run] [--schedule]` (the worker runs it every morning once sourcing has started; reminders go after `rfq_reminder_after_days` working days, at most `rfq_max_reminders`).
- Make purchase orders from the lines that are ready (contract prices, direct buys the route allows, and awarded quotations): `python -m p2p.cli order <tenant> [--request NO]` (the worker does it when a contract line is sourced or an RFQ is awarded). Quotes are entered by a buyer on the RFQ page, where the buyer selects the supplier (step 6): quotes failing a must-have are dropped with the reason, the rest ranked on total cost (GST not counted when the credit is claimed) or a weighted score, by the versioned `supplier_selection_rule`; a line is split between suppliers only when the saving beats the extra freight; anything but the recommendation, or too few qualifying quotes, needs a written reason; one order per supplier, set of terms and delivery location. Who approves is the order's tier, the `po` rows of `approval_rule` (Apex: up to Rs 1,00,000 only a touchless order, approved by the rule; purchase manager to 5,00,000, including any order below that is not touchless; director above). Whoever made or submitted an order never approves it, at any value (`orders/workflow.makers`). A touchless order (D35: only contract and safe-reorder lines, in the touchless band, within `touchless_rule`'s limit and 2% of the estimate, active supplier, contract room, budget fine) is issued and sent by the system when the autonomy gate `po.issue` is automatic (on for Apex, off for Brightwave, from `autonomy:` in `company.yaml` at demo reset); otherwise its note says why it went to a person.
- Run the strategic review detectors once (contract prices against verified, fresh, in-region benchmarks by the versioned `price_threshold_rule`; contracts near their end): `python -m p2p.cli review <tenant> [--dry-run]` (the worker runs them daily and when a benchmark is verified).
- Ask requesters to confirm their services at the end of a period (one email each, a signed link per service line that works once): `python -m p2p.cli confirm-services <tenant> [--dry-run]`. A service line (item or category of kind service) is confirmed by the person who asked for it (**Confirm services**), never received by the store; its invoice is held `service_not_confirmed` until then. Goods with no order go through **Receive without order** (purchase manager's proposal, the buyer's after-the-fact order, then the normal receipt).
- Evals against the plan, with independent oracles (separate from the tests): `python evals/run.py [--live] [--only E04,E09] [--quick]`; see `evals/README.md`. Run them before calling a phase done.
- The demo companies: `python -m p2p.cli demo reset apex` (the main one, Apex Pumps: a pump plant at Chakan and a new one at Sanand with no history, 10 people (nine roles and a second administrator), 16 items, 6 active suppliers plus a blocked one and two prospects, market benchmarks, twelve months of stock history) or `demo reset brightwave` (IT services), from `backend/` (drops and makes the tenant; role logins like `buyer@apexpumps.example`, all with the throwaway dev password in `demo.DEV_PASSWORD`, also listed in `.dev-credentials`; refuses a non-local database). Script: `docs/demo-script.md`; evals E33 and E34. A reset ends live (readiness must pass); `demo reset apex --state setup` leaves it in setup for a go-live rehearsal. To start mid-flow instead, `python -m p2p.cli demo populate apex [--reset]` fills it with live cases at every stage (`platform/demo_cases.py`; drives the real API as the role logins; refuses a company that already has requests).
- Company states (D-04; block 0d): a company is setup, cutover, live or suspended. The platform team, from `backend/`: `python -m p2p.cli company state <slug> [setup --reason R --operator N]` (history; back from cutover), `company readiness <slug> [--group all|setup|cutover] [--json]`, `company cutover <slug> --reason R --operator N [--dry-run]` (the setup database becomes an archive `<db>__setup_<time>` and a clean one is made with the configuration, `platform/cutover.py` `CARRIED`), `company cutover-import <slug> <folder> --as EMAIL [--dry-run]` (the open documents of the old system: a dataset's `cutover/`), `company suspend <slug> --kind commercial|security ...`, `company resume ...`, `company archives <slug>`, `user repair <tenant>`. Exit 0 done, 1 refused by the data, 2 refused by the state. Go-live is the company's: an administrator proposes it on the Go-live tab of the admin setup (`POST /api/company/go-live`), another approves it. Imports follow the state (`company_state.require_state`); after go-live a masters import never adds or changes opening stock or bank accounts, and the stock history import is refused.
- Regenerate data: `python -I datagen/generator/company_profile.py apex` (or `brightwave`) writes `data/datasets/apex-v1/` from `datagen/catalog/apex/company.yaml`; `--check <dataset>` checks it. Evals use `apex-v1` (`P2P_EVAL_DATASET` picks another).

## Rules

1. **Money is always `Decimal`**, quantised to paise. Never float for money, tax or quantity.
2. **A model never computes a number a decision uses.** Totals, tax, TDS, due dates and match results come from code in `formulas/` or `rules/`. A model may extract, classify, draft or explain.
3. **Three building blocks.** A *service* is deterministic. An *AI step* is one model call with schema validation and an evidence check. An *agent* is a tool loop. Use the simplest one that works.
4. **Every write goes through a service that writes the audit log.** No route or agent writes to the database directly.
5. **Sensitive actions are proposals.** Payment runs, vendor activation, releasing a payment block, accepting a price variance and approvals above a limit create a proposal that a person approves. Agents and services never execute these themselves.
6. **Tenant safety.** One database per tenant plus a control database. A request without tenant context is refused. A test must prove tenant A cannot read tenant B.
7. **Segregation of duties:** requester, approver, receiver, invoice approver and payer differ for the same case.
8. **Rules and rates are data, not code.** Approval matrices, tolerances, GST rates and TDS sections live in versioned tables. A decision stays reproducible against the version it used.
9. **Dates and time.** Store timestamps with time zone; business logic uses the financial year (April to March) and the business calendar with holidays.
10. **No secrets in the repo or in chat.** `.env` is git-ignored; the owner enters API keys manually. Development uses synthetic data only.
11. **Two database logins.** The app (API, worker, every command but migrations and company create/drop) signs in as `<control db>_app` (`APP_DATABASE_USER`, `APP_DATABASE_PASSWORD` in `.env`) with select, insert, update and delete only; it owns nothing. The owner login (`CONTROL_DATABASE_URL`) is for migrations and creating and dropping companies only (`tenants.owner_engine`, never in a service or an API). A migration that adds an insert-only table revokes update and delete from the app in the same migration.
12. **Free and open-source tools only** (see the Tech Stack sheet in the plan). Do not add a dependency without checking its licence and that the package is the real one.

## Generated data safety

Generated PANs always carry the digits `0000` (never issued), phones are `+91 00000 …`, emails end in `.example`. Keep it that way.

## Definition of done for a task

Code, tests (including boundary cases for formulas), `python scripts/check.py` green, audit rows written for any write, docs updated if the data model changed (after a migration run `scripts/gen_schema_doc.py`; a test fails if `docs/database-schema.md` is stale).

## Style

Match the surrounding code. Short plain-language comments only where the reason is not obvious. Keep documents simple and short.

**Write modular, reusable, simple code:**

- **Reuse first.** Before writing anything new, look for an existing service, formula, helper or screen that does it, and use or extend that. Never copy and paste logic; move shared code into one place.
- **Small modules, one job each.** A module owns one area; a function does one thing and stays short. Keep the package boundaries in the layout above.
- **Use classes (OOP) where they fit:** for a real thing with its own state or rules (an importer, a connector, a mailbox, a document), or a shared interface with several versions (one base class, one subclass per ERP or file format). Plain functions are fine for simple steps; don't wrap them in classes for the sake of it.
- **Keep it simple.** Build only what the current step needs: no extra features, layers, settings or abstractions "for later". The simplest code that passes the tests wins.
